Team Setup and Budgeting
This section could also be named thus: Software Application Discovery as The Best Method for Estimating the Application Software Development Budget.
Discovery is a process where a project team discovers all technical requirements related to a given project, so they can prototype the application and estimate the budget. So, not only can you discover all the technical requirements, but you can also see how an app would look like and figure out how much the entire process is going to cost. We just saw how to do use User Stories to capture, from the outside, what the system should be doing. Prototyping helps us flesh out a little bit of that functionality into something that works.
Thanks to the prototype, users can get to see how an app looks and feels like. A prototype is a semi-functional graphical representation of a potential product that offers an overall look and user flow for examination before any real development begins. Prototypes often look so natural and complete that they can be handed off to a potential user for the feedback!
By the end of the discovery cycle, the following items are delivered to the stakeholders:
Requirements’ definition and analysis: These elements offer a review of key aspects, critical functionality, and core technical features. The project team, to achieve this, dives into the initial requirements, making them more coherent and tying the various proposed elements to each other. Recommended technological stack: An outline of the programming languages and technologies that will best suit the requirements. Often, a comparative table is used to present the pros and cons of each recommended approach. Functional and non-functional requirements: This captures the details of the potential product, including vision, scope, and a description of user functionality. Project plan: A step-by-step plan for how the project should run to achieve on-time and on-budget delivery. Cost estimation: Detailed cost estimates that provide granular analysis. Usually, at this point, estimates are so precise that budget overruns rarely happen.
From a business perspective, discovery helps uncover new opportunities and/or verify a business idea. The results of this process might influence or even shift the direction of any further product development. This method provides invaluable insights at a very early stage. By investing time in discovery, you can minimize the project risks associated with cost and schedule overruns.
Discovery also helps with budgeting. Given the capacity of a team, as this is being revealed through the discovery process, one can define the monthly cost of that team. Instead of trying to define all sides of the scope, quality, and timescale triangle we can do budgeting on a running basis. We know what we have to pay the team and we know how much can the team deliver over a time frame. For as long as there is value to be had by the work of the team, we can keep going. There are different reasons to do something. For example, if we anticipate that the language/technology we use will have to change, because it is getting inefficient, then although there will be no immediate gain, we know we should spend the effort and time to do so. 

The Plan – Build – Review – Retrospect cycle	
For Agile the core is about incremental, iterative development, with short feedback loops. Organising the work follows this pattern. We do some planning, we build something, we get some feedback, we try to figure out what went ok and what not, and then we repeat.
There are different approaches on how exactly to do that. Scrum, for example, has created a whole methodology out of these ideas. Other approaches are more agnostic or permissive, if you will, about the specific ways in which the above principle will be implemented.
The main thing is to implement this cycle, effectively.
Information radiators
Communication, between team members, and between the team and stakeholders, is fundamental for Agile to work. There cannot be any self-organising taking place without the free flow of information. Information radiators are all these devices that collect and then, passively, disseminate the pieces of information among the team and stakeholders. They make key project information visible to everyone, all the time, without requiring people to ask. Common examples are task boards, burndown/burnup charts, and blocker/kanban-style visualizations — anything that continuously communicates progress or constraints, so that the participants can act upon any potential problem.

Kanban board
The board is one of the main tools used by the Kanban framework, as we saw earlier. It brings together some of the tools we have seen already: the tasks the grew out of the user stories, which are entries in the board’s columns, the quality standards guarder by the definition of ready and the definition of done for these tasks, and the flow of work regulated by the per column limit of the work-in-progress. 
Using a Kanban board helps teams visualize their workflow, identify bottlenecks, and improve efficiency by limiting work in progress. As all information radiators, it promotes transparency, making it easy for everyone to see the status of tasks and prioritize work effectively.
Kanban boards are especially useful for teams with unpredictable workloads or frequent changes in priorities. For example, support teams can quickly adapt to new requests, while development teams can quickly prioritise and work with bugs, as they arise, along with other development tasks. This flexibility leads to continuous delivery and better project collaboration across the team.

Metrics
Each framework has its own metrics tied to it. Scrum has team velocity (the amount of work, measured in story points, a team can complete during a single sprint), and burndown chart (a visual graph that shows the amount of work left in a sprint and the time left to finish it). Kanban uses Lead Time (starts when a customer or stakeholder requests something and ends when the result is delivered) and Cycle Time (starts when the team actively begins working on an item and ends when it's completed)
As Goodhart's Law states, “When a measure becomes a target, it ceases to be a good measure.” Metrics can be gamed. Simple example of paying bonuses for bugs found, creates incentive to create bugs (https://devhumor.com/media/dilbert-s-team-writes-a-minivan).
Let us see an example. In the DevOps framework, Deployment Frequency measures the number of times that code is deployed into production. It’s usually reported in “Deployments Per Day”. Mean Lead Time for Changes Mean Lead Time for Changes is the average time it takes from code being committed to that code being released into production. Some organizations begin tracking the time from the first commit of the project’s code, while others measure it beginning from merging the code to the main branch. Mean Time to Recovery (MTTR) This metric measures the average time it takes the team to recover from a failure in the system. “Failure” can mean anything from a bug in production to the production system going down. Change Failure Rate Change Failure Rate measures how often a code change results in a failure in production. Changes that result in a rollback, in production failing, or in production having a bug all contribute to this metric.
The first two metrics — Deployment Frequency and Mean Lead Time for Changes — measure the velocity of a team. MTTR and Change Failure rate are a measure of the quality and stability of a project. All four metrics can be derived from mining the tools that you are currently using.
When the purpose for metrics is misunderstood, serious issues can occur. We are increasingly seeing DORA metrics used as goals, complete with OKRs (objectives and key results) where the objective is “improve DORA metrics.” But improving metrics should never be your goal. Related to this is the idea of using DORA metrics to compare delivery performance between teams. Every team has its own context. The product is different with different delivery environments and different problem spaces. Another common problem is the growth of “vanity radiators,” metric dashboards that display numbers but give no obvious clue about what action to take. “We deployed 436 times!” OK, but how big is the organization? Was those 436 times in a week, a day, or a year? Is that number improving or degrading?
